# Сайты и SEO — надстройки + дисциплина изменений

Два слоя в одном модуле: **SEO-инструменты** (что делать с трафиком) и **правила работы с сайтами** (как не сломать прод, когда правишь). Триггерится на «собери семантику», «технический аудит», «топик-кластеры», «on-page», «правлю сайт / перед деплоем / откати».

> Часть SEO-задач **может требовать ключей** (Google Search Console, индекс-API, платные семантические сервисы). Это **опционально** — без ключей работает на открытых данных и ручном вводе. Ключи — только в `.env` проекта, в `STACK.md` указатель, в `.md` значения не пишем.

## Слой 1 — SEO-надстройки

### Семантика
- Сбор и кластеризация запросов: head/mid/long-tail, по интенту (информационный / коммерческий / навигационный / транзакционный).
- Группировка в **топик-кластеры**: одна pillar-страница + сателлиты, перелинковка внутри кластера.
- Карта «запрос → страница»: один интент = одна страница, без каннибализации.

### On-page
- Title/description/H1 под интент, без переспама; один H1, логичная иерархия H2/H3.
- Структура контента под запрос (ответ в первом экране, FAQ под long-tail, таблицы/списки где уместно).
- Внутренняя перелинковка, анкоры по смыслу, хлебные крошки.
- Микроразметка (Schema.org: Article/Product/FAQ/Breadcrumb) где применимо.

### Технический аудит
- Индексируемость: robots.txt, meta robots, canonical, sitemap.xml, коды ответа.
- Скорость/Core Web Vitals (LCP/CLS/INP), вес страницы, lazy-load, кэш.
- Дубли, битые ссылки, цепочки редиректов, пагинация, hreflang (если мультиязычность).
- Мобильная версия, HTTPS, структура URL.

### Топик-кластеры (рабочий порядок)
1. Pillar-тема → подтемы (из семантики).
2. На каждую подтему — страница с своим интентом.
3. Перелинковка: сателлиты → pillar и между собой по смыслу.
4. Контроль каннибализации: одна страница на интент.

### Где нужны ключи (опционально)
- **Google Search Console** — реальные запросы/позиции/CTR. Без него — ручной экспорт или открытые источники.
- Индекс/инспекция-API, платные сервисы семантики — по желанию.
- Ключи → `.env` проекта (напр. `GSC_CREDENTIALS`), в `STACK.md` только указатель. В `.md` секреты не пишем.

## Слой 2 — Правила работы с сайтами и логгирования

> Best-practice дисциплина изменений. Цель — любую правку можно объяснить, проверить и откатить. Применяй к любому сайту/репозиторию, без привязки к конкретным доменам.

### Чеклист ПЕРЕД правкой
- [ ] Понятно, **что** и **зачем** меняем (одна формулировка цели).
- [ ] Знаю, **какие страницы/шаблоны/файлы** затронет (а не «примерно тут»).
- [ ] Есть **бэкап / коммит / точка отката** до правки (рабочая ветка, не прямо в прод).
- [ ] Проверил, не сломает ли это **индексацию** (canonical, robots, редиректы, URL).
- [ ] Договорился, **как проверю результат** (что считаю «получилось»).

### Лог изменений (вести всегда)
На каждую правку — запись в лог проекта (`Projects/<сайт>/CHANGELOG.md` или `_BRAIN/Выводы/`):
```
## ГГГГ-ММ-ДД — <короткое что сделали>
- Что: <изменение>
- Зачем: <причина / гипотеза>
- Затронуто: <страницы/файлы/шаблоны>
- Откат: <как вернуть: коммит/ветка/бэкап>
- Проверка: <что и как проверили>
```
Лог — чтобы через месяц понять, почему позиция/трафик дёрнулись, и что откатывать.

### Проверка ПЕРЕД деплоем
- [ ] Локально/на стейдже открывается, ключевые страницы не упали (200, а не 4xx/5xx).
- [ ] Не сломаны canonical / sitemap / robots / редиректы.
- [ ] Нет случайного `noindex` и закрытия от индексации.
- [ ] Внутренние ссылки и формы живые; нет битых ассетов.
- [ ] Метрики/счётчики на месте.
- [ ] Знаю команду **отката** на случай регресса.

### Откат
- Откат = один шаг (revert коммита / переключение ветки / восстановление бэкапа), а не «чиним на проде вручную».
- После отката — запись в лог: что откатили и почему.
- Правило: **не правим прод напрямую**; меняем в ветке/стейдже → проверка → деплой → наблюдение.

### Дисциплина (коротко)
- Одна правка — одна цель — одна запись в логе.
- Любое изменение обратимо (есть точка отката).
- SEO-критичное (URL, canonical, robots, редиректы) — отдельная проверка перед деплоем.

## Границы (что НЕ делает)
- Не пишет продающий/редакторский текст → это `writer`.
- Не деплоит сам без подтверждения и без пройденного чеклиста.
- Не лезет в прод напрямую и не делает необратимых правок без точки отката.
- Секреты (ключи GSC и пр.) — только в `.env`, в `STACK.md` указатель, в `.md` не пишем.
